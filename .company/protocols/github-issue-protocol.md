# GitHub Issue 運用プロトコル

## 目的

**同じ間違いを繰り返さないためのナレッジ管理基盤。**

Issueとコメントに「何が起きて、何を学んだか」を蓄積し、
未来のセッションで参照して判断の質を上げる。

**対象リポジトリ:** `yukiko10140422-star/trustport`

## 3つの運用原則

1. **蓄積優先** — 「未来の自分が読んで役立つか」を基準に書く
2. **コメント集約** — 同一テーマの更新は既存Issueのコメントに追記（重複Issue禁止）
3. **教訓必須** — Issue完了時に学び・次回への注意点を必ず残す

## ラベル体系

### PDCAフェーズ（必須・1つ選択）
| ラベル | 用途 |
|--------|------|
| `pdca:plan` | 計画・企画・調査段階 |
| `pdca:do` | 実行・作業中 |
| `pdca:check` | 評価・振り返り・検証 |
| `pdca:act` | 改善・是正アクション |

### 部署（必須・1つ以上選択）
全14部署: 秘書室 / PM / リサーチ / マーケ / 開発 / 経理 / 営業 / クリエイティブ / 人事 / 法務 / 物流 / eBay / アパレル / DX

### 優先度（任意）
`priority:高` / `priority:通常` / `priority:低`

### タイプ（任意）
| ラベル | 用途 |
|--------|------|
| `type:情報共有` | 全社アナウンス・ナレッジ共有 |
| `type:意思決定` | CEOの方針決定・判断事項 |
| `type:週次レビュー` | 週次PDCA振り返り |
| `type:教訓` | 失敗・手戻り・学びの記録（再発防止） |

## コメント運用

- 同一テーマの進捗・更新 → 既存Issueの**コメント**に追記
- コメントフォーマット: `### [更新種別] YYYY-MM-DD` + 内容 + `更新者: [部署名]`
- 新規Issue起票は「既存と異なる新しいタスク・議題」の場合のみ

## 教訓の記録（最重要）

Issue完了（Close）前に必ず以下のコメントを残す:

```markdown
### [教訓] YYYY-MM-DD

#### うまくいったこと
- ...

#### うまくいかなかったこと
- ...（原因: ）

#### 次回への注意点
- ...

---
更新者: [部署名]
```

重大な失敗・手戻りは `type:教訓` で独立Issueとして起票する。

## 全部署共通ルール

- 作業開始前に `gh issue list --label "dept:自部署"` で関連Issue・過去の教訓を確認
- 作業完了時は成果・学びをIssueコメントに残す
- 失敗・手戻りは原因と対策を明記する
- Close前に教訓コメントを必ず残す

## 秘書の運用

- 応答開始時: `gh issue list` で全Issueの状態を確認
- 応答開始時: `gh issue list --label "type:教訓"` で教訓を確認
- 応答中: 関連Issueにコメントで進捗記録、必要に応じて起票
- 応答終了時: Issue変更があれば報告

## .company/ との連携

- GitHub Issue = 可視化・追跡・教訓蓄積
- .company/ = 詳細ドキュメント・作業ファイル
- Issue本文に `.company/` 内のファイルパスを記載して紐付ける
- 意思決定は `ceo/decisions/` にもログを残す
