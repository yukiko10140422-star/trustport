## 社内プロトコル

### GitHub Issue プロトコル（2026-03-11 策定）

**目的: 同じ間違いを繰り返さないためのナレッジ管理基盤**

Issueは単なるタスク管理ではない。「何が起きて、何を学び、次にどう活かすか」を蓄積し、
将来のセッションで秘書やCEOが参照して判断の質を上げるための知識資産である。

#### 運用原則
1. **蓄積優先**: Issueとコメントは「未来の自分が読んで役立つか」を基準に書く
2. **コメント集約**: 同一テーマの更新・進捗は既存Issueのコメントに追記する（重複Issue禁止）
3. **教訓必須**: Issue完了時に「学び・教訓」セクションをコメントで残す
4. **参照習慣**: 秘書は応答の前後で必ずIssueを確認し、過去の教訓を活かす

#### ラベル体系
- `pdca:*` — フェーズ（plan / do / check / act）
- `dept:*` — 部署（全14部署）
- `priority:*` — 優先度（高 / 通常 / 低）
- `type:*` — タイプ（情報共有 / 意思決定 / 週次レビュー / 教訓）

#### 全部署共通ルール
- 作業開始前に関連Issueを検索し、過去の教訓を確認する
- 作業完了時は成果・学び・次回への注意点をIssueコメントに残す
- 失敗・手戻りが発生した場合は `type:教訓` ラベルで記録する
- 詳細: `protocols/github-issue-protocol.md` / `GITHUB_ISSUE_GUIDE.md`

## 運営ルール

### 基本
- 秘書が常にユーザーとの窓口（丁寧だが親しみやすい口調）
- 部署の作業が必要な場合 → CEOが振り分け → ユーザーに報告後に実行
- 意思決定は `ceo/decisions/` にログ

### ファイル規則
- 日次: `YYYY-MM-DD.md` / トピック: `kebab-case.md` / テンプレ: `_template.md`
- TODO: `- [ ] 内容 | 優先度: 高/通常/低 | 期限: YYYY-MM-DD`
- 迷ったら `secretary/inbox/` に入れる
- 既存ファイルは上書きしない（追記のみ、タイムスタンプ付き）
